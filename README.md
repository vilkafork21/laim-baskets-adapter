# laim-baskets-adapter

Первая нода мониторингового контура LAIM. Принимает **эталонную корзину
GenAI-агента** (одна XLSX-книга) и **три документа** (отчёт о валидации, отчёт
о разработке, инструкция ассессора) и превращает их в машиночитаемый вход
всего остального контура:

1. **корзину в формате тестового датасета** — единый табличный формат,
   который дальше понимают все ноды;
2. **контракт метрики** — как именно считать ключевую метрику (КМ) на этих
   данных;
3. **значение КМ** — заявленное в отчёте о валидации и пересчитанное по корзине;
4. **журнал прогона** — что нода решила, что проверила и почему.

## Зачем нода нужна

Корзины приходят от разных команд и физически не похожи друг на друга: шапка
на второй строке под баннером объединённых ячеек, диалог, упакованный в одну
ячейку, оценки трёх разметчиков в трёх колонках, веса-частотности, листы
справочников рядом с листом данных. Отчёты о валидации тоже разные: КМ бывает
объявлена одной фразой («Accuracy с порогом 90%»), а бывает таблицей по
критериям. Нода снимает эту разницу: вниз по контуру всегда уходит один и тот
же формат.

## Философия: LLM понимает — код исполняет и измеряет

Ключевое проектное решение: модель (glm-5.2 через контурный шлюз) **читает
документы и структуру книги и возвращает компактный маппинг** («лист такой-то,
запрос в колонке A, оценка в C, группировка по merge»), а всё остальное делает
детерминированный код: применяет маппинг к данным, строит канон, считает КМ,
публикует. Модель никогда не переписывает сами данные — это защита от
галлюцинаций и независимость стоимости от размера корзины.

Второе решение: **деградация вместо падения**. Код проверяет физику
(исполним ли маппинг на этой книге) и обязательные поля формата — но не
«честность» модели. Почти любая проблема превращается в статус с причиной и
записью в журнале, а корзина публикуется всегда, когда её удалось собрать.

## Место в контуре

```text
корзина XLSX + 3 DOCX/TXT
        │
        ▼
 laim-baskets-adapter ──► reference_umr      ─► g-aiva-doc-browser, laim-kriteria-selector,
        │                                       laim-asessor-agent, drift/oos-тесты
        ├──────────────► monitoring_metric   ─► laim-kriteria-selector (identity-гейт)
        ├──────────────► km_result           ─► журнал прогона (в port_wiring не подключён)
        └──────────────► umr_artifact        ─► путь к XLSX (в port_wiring не подключён)
```

## Порты

### Входы (все обязательные; платформа отдаёт локальный путь)

| Порт | Что это |
|---|---|
| `test_set` | XLSX-корзина (`.xlsx`/`.xlsm`; тип определяется по содержимому, не по расширению) |
| `validation_report` | DOCX-отчёт о валидации — **приоритетный источник имени и значения КМ** |
| `development_report` | DOCX-отчёт о разработке (часто содержит расшифровку колонок корзины) |
| `assessor_instruction` | Инструкция ассессора: DOCX либо UTF-8 TXT |

### Выходы

| Порт | Тип | Что отдаёт |
|---|---|---|
| `reference_umr` | dataframe | Корзина в формате тестового датасета (см. «Форматы выхода») |
| `monitoring_metric` | default | Контракт `laim-monitoring-metric.v2`: как считать метрику мониторинга |
| `km_result` | default | Журнал прогона `laim-run-report.v1` (см. «Наблюдаемость») |
| `umr_artifact` | default | Локальный путь к XLSX с тем же листом |

### Настройки ноды

| Настройка | По умолчанию | Зачем |
|---|---|---|
| `model_id` | `glm-5.2` | Модель контурного шлюза |
| `sheet_name` | пусто | Жёстко задать лист книги. Нужен, когда в книге листы **разных** агентов: автовыбор в этом случае ненадёжен. При заданном листе перебор других запрещён |

## Как проходит прогон

```text
1. Чтение          пакет → сырые гриды книги + структурный текст документов
2. LLM «разметка»  документы целиком + снимок книги → маппинг колонок (JSON)
3. Физика          код доказывает исполнимость маппинга, строит канон
4. LLM «метрика»   документы + инвентарь колонок → план расчёта КМ (JSON)
5. Расчёт          движок: оценка каждой единицы; КМ — заявленная в отчёте
6. Публикация      лист спеки + XLSX + журнал в порт km_result
```

Подробно по шагам:

**1. Чтение.** Файлы пакета классифицируются по содержимому OOXML (книга — по
каталогу `xl/`, документ — по `word/`). Книга читается в сырые гриды дважды:
значения и карта формул, плюс merged-диапазоны. Документы превращаются в
структурный текст: заголовки Word получают `#`-префикс, **строки таблиц
сериализуются через ` | `** (иначе «Accuracy | 0.93 | порог 0.9» рассыпается
на несвязанные абзацы — а КМ в отчётах о валидации объявляется в том числе
таблицами). Роли документов известны из портов; если имена файлов произвольные,
они узнаются по номенклатуре процесса
(«валидац…» / «разработ…» / «инструкц…»).

**2. LLM-задача «разметка».** Модель получает полные тексты трёх документов
(каждый в XML-теге своей роли) и **снимок** книги: якорные строки (первые
строки листа и строки смены структуры), статистику каждой колонки (заголовок,
непустые, числовые, сэмплы, уникальные значения), merged-диапазоны и дословные
маркеры диалога, если они видны в данных. Самих данных модель не видит —
снимок не растёт с числом строк корзины. Ответ строго по JSON-схеме: лист,
строки шапки, роли колонок адресами (`A`, `B`, …), группировка
(`none | column | merged_rows | blob_row`), упакованный диалог с маркерами
реплик, weight-колонка.

**3. Физика разметки и канон.** Код проверяет только то, без чего маппинг
неисполним: границы данных (по непустым `input_query`, с учётом merge и
формульных итоговых строк), существование колонок, «одна колонка — одна роль»,
физическое подтверждение группировки (vertical merge принудительно даёт
`merged_rows`), целые веса. Затем строится канонический фрейм и проверяются
обязательные поля формата. Любое нарушение уходит модели как repair с точным
текстом ошибки — до 3 попыток; построчные дефекты (пустой `input_query`,
строки вне групп, неразворачиваемые blob-строки) после исчерпания repair
отбрасываются с перечнем строк в журнале, а несобираемый лист отвергается в
пользу запасного.

**4. LLM-задача «метрика».** Модель получает документы и инвентарь колонок
канона и отвечает по схеме: имя КМ, метод расчёта, источники-колонки,
редьюсер, политика пропусков, шкала, **заявленное в отчёте о валидации
значение** (`raw` — дословный текст числа: «93%», «0,9736») и порог релиза.
Приоритет источника КМ: отчёт о валидации → отчёт о разработке → корзина.
Цитату `raw` код проверяет по тексту отчёта о валидации: не найдена дословно —
план отклоняется в repair. Режим оценки модель **не выбирает** — его
определяет форма данных (см. ниже).

**5. Расчёт.** Движок считает оценку каждой единицы наблюдения (колонка
`main_metric`) в `Decimal`. **Значение КМ — всегда заявленное в отчёте о
валидации**; пересчёт по корзине публикуется рядом как информационное поле
(`recomputed_value`), а их расхождение — пометкой `reconciliation: mismatch`
с допуском в один последний опубликованный разряд («0.93» → 0.01). Никаких
действий по расхождению нет: методика отчёта может законно отличаться от
построчного среднего (пример — взвешивание по частотам запросов). Нет
значения в отчёте — нет КМ: `official_baseline_missing`, дефект артефактов.

**6. Публикация.** Фрейм проецируется в лист спецификации, пишется XLSX и
`run_report.json`; журнал уходит в порт `km_result`.

Прогон читается сверху вниз: что прочитали → что решила модель → что доказал
код → сверка → итог. Отклонённая repair-попытка выглядит так:

```text
WARNING laim_basket.llm.client: layout: попытка 1/3 отклонена — LayoutError: Dialogue blob содержит непустые строки, которые нельзя полностью развернуть | детали: {"invalid_rows": [...], "invalid_count": 268}
```

## Форматы выхода (`reference_umr`)

Два взаимоисключающих варианта — листы спецификации «Формат тестового датасета»:

- **«Вариант для отд. запросов»** (flat): строка = один запрос. Колонки:
  `query_id`, `input_query`, `output_answer` (обязательные), затем по наличию —
  `scenario`, `session_id`, `solution_version`, `input_query_count` (вес),
  эталоны (`reference_answer` при одном, `reference_answer_1..N` при
  нескольких — нумерация спецификации), `<имя>_metric` (исходные оценки),
  `main_metric`, `assessor_id`.
- **«Вариант для диалога»**: строка = одна сессия. Колонка `dialogue` — список
  троек `(query_id, input_query, output_answer)`, плюс `session_id`,
  `<имя>_metric`, `main_metric`; при взвешенном редьюсере — `input_query_count`
  (вес сессии, который контракт называет `weight_column`).

Публикуются только канонические имена из словаря спецификации (сырые колонки
корзины остаются в debug-отчётах). Единственная колонка сверх словаря —
`main_metric`, оценка единицы по плану измерения: её читают потребители
контура (`score_column` контракта `monitoring_metric`).

## Единица оценки — от формы данных, не от мнения модели

| Физическая форма корзины | Режим | Единица наблюдения |
|---|---|---|
| Обычные Q/A-строки без группировки | `qa` | строка |
| Диалог, упакованный в одну ячейку (`blob_row`) | `dialogue` | сессия |
| Группы строк, оценка стоит один раз на группу (vertical merge) | `dialogue` | сессия |
| Группировка по колонке / оценка на каждую реплику | `turn_with_history` | реплика с историей |

Один `session_id` сам по себе не делает корзину диалоговой: группировка должна
быть видна в данных. В режиме `dialogue` сессия — одно наблюдение, длинные
диалоги не перевешиваются числом реплик.

## Падение vs деградация

Нода **умирает только от трёх причин** (исключения — потомки `BasketError`
с `reason_code`; детали всегда печатаются в лог платформы до re-raise):

| Причина | reason_code |
|---|---|
| Битый пакет: не 1 XLSX + 3 документа, нечитаемые файлы | `package_error`, `read_error` |
| LLM недоступна после транспортных ретраев | `llm_error` |
| Обязательные поля спеки не собраны после repair и запасного листа | `spec_error` |

Всё остальное — **деградация**: статус + причина + запись в журнал, корзина
публикуется:

| Событие | Реакция |
|---|---|
| КМ не объявлена в отчёте о валидации | `monitoring_metric: not_computable`, `official_baseline_missing` |
| КМ объявлена неоднозначно (несколько кандидатов) | `not_computable`, `ambiguous_baseline` |
| План метрики не построен (repair исчерпан; +1 запасной лист, если он не задан оператором) | `not_computable`, корзина публикуется без метрик |
| Пересчёт расходится с заявленной КМ | публикуется заявленное; `reconciliation: mismatch` — информационная пометка, действий нет |
| Частично пустые `input_query` (flat) | строки отброшены, перечень в журнале |
| Часть blob-строк не разворачивается в реплики | repair (маркеры/контейнер могли быть выбраны неверно), затем отброс этих строк с перечнем в журнале |
| Пустой `input_query` или строка вне групп (в любой форме корзины) | repair, затем отброс строк с перечнем в журнале |
| Пропуски в колонке `session_id`/`query_id` | фолбэк на номер группы/строки, WARNING `*_source_rejected` |
| Разметка не собралась на листе (repair исчерпан) | лист отвергается, разметка пробуется на запасном — как у этапа метрики |
| Нечисловое значение в score-колонке («Рекомендации» среди 1/0) | пропуск по `missing_policy`, WARNING |
| CI-код не найден в имени пакета | `basket_id` = имя пакета, WARNING |
| Отчёт о валидации упоминает другой CI-код | baseline берётся из отчёта как есть, WARNING `report_identity_mismatch` |

## LLM-слой

- **Транспорт**: OpenAI-совместимый `/chat/completions` контурного шлюза
  sds-ai-gateway; модель задаётся настройкой ноды `model_id`, сэмплирование
  детерминированное (`temperature=0`).
- **Structured output с пробой**: первый вызов уходит с
  `response_format: json_schema`; если шлюз отвечает HTTP 400 — повтор без
  него, и до конца прогона используется текстовый JSON (итог пробы виден в
  журнале: `llm.structured_output`). Локальная валидация по схеме выполняется
  всегда, независимо от исхода пробы.
- **Repair**: невалидный ответ (схема или физика) возвращается модели с точным
  текстом нарушения и деталями; до 3 попыток на задачу. Причина каждой
  отклонённой попытки — WARNING в логе.
- Реальность контурных reasoning-моделей учтена: `<think>…</think>` вырезается,
  обрыв по токенам удваивает `max_tokens` до потолка, транспортные ошибки
  ретраятся с backoff.

## Наблюдаемость

Каждое событие пишется **одновременно** в `logging` и в журнал, который уходит
в порт `km_result` и в файл `run_report.json` — поэтому прогон читается даже
там, где платформа теряет stdout. Структура журнала (`laim-run-report.v1`):

```json
{
  "contract_version": "laim-run-report.v1",
  "basket_id": "CI0XXXXXXXX",
  "status": "computed",
  "km": {"name": "...", "value": 0.9736, "recomputed_value": 0.97368,
          "scale": "ratio", "reconciliation": "match",
          "coverage": {"total_units": 266, "scored_units": 266, "...": "..."}},
  "decisions": {"sheet": "Sheet1", "grouping": "merged_rows",
                 "assessment_mode": "dialogue", "metric": "...",
                 "method": "identity", "reducer": "mean"},
  "stages": [{"stage": "read", "ms": 169, "outcome": "ok"}, "..."],
  "llm": {"model": "glm-5.2", "structured_output": true,
           "calls": 2, "repair_turns": 0, "transport_retries": 0},
  "warnings": [],
  "dropped_rows": {},
  "input_sha256": {"test_set.xlsx": "..."}
}
```

При сотне корзин триаж делается по этим JSON без чтения логов: агрегируйте по
`status`, `warnings[].code`, `km.reconciliation`. Каталог `debug/` (дампы
каждого HTTP-вызова LLM и промежуточные артефакты) пишется рядом с результатом
прогона, но в ноде умирает вместе с контейнером — источником истины о прогоне
служит журнал в порту.

## Карта кода

```text
main.py                    порты платформы, сборка контракта monitoring_metric
laim_basket/
  pipeline.py              оркестрация этапов, деградация, запасной лист
  llm/tasks.py             две LLM-задачи, сборка контекста, проверка цитаты КМ
  llm/prompts.py           тексты промптов (документы в XML-тегах, схема в конце)
  llm/schemas.py           JSON-схемы двух LLM-ответов (quotes первыми)
  llm/client.py            транспорт: response_format-проба, repair-петля, ретраи
  resolve.py               физика разметки: границы, роли, группировка
  metric/resolve.py        физика плана: контракт источников, шкалы, режим оценки
  metric/engine.py         расчёт: 6 методов, 2 редьюсера, missing_policy
  evidence/workbook.py     снимок книги для промпта (якоря, статистика, маркеры)
  reading/                 package_scan (классификация файлов), xlsx_reader
                           (сырые гриды + формулы + merge), docx_reader
                           (структурный текст), formulas, headers
  transform/               grouping (merge/column/blob), canon, identity,
                           region, values — детерминированный исполнитель маппинга
  umr_schema.py            обязательные поля формата тестового датасета
  publish.py, export/      проекция в листы спеки, запись XLSX
  journal.py               журнал прогона laim-run-report.v1
  models.py                dataclass-контракты между слоями
  errors.py                иерархия BasketError с reason_code
  config.py, defaults.py   адрес контурного шлюза, технические константы
```

Методы расчёта КМ (`metric/engine.py`): `identity` (готовая оценка),
`accuracy` (prediction vs target по labels), `mean_criteria`/`all_criteria`
(среднее/минимум по критериям), `majority`/`all_assessors` (голоса
разметчиков); редьюсеры `mean` и `frequency_weighted_mean` (вес —
`input_query_count`); политика пропусков `fail | exclude_unit |
exclude_value | zero`.

## Что делать, если…

- **`monitoring_metric.status = not_computable`** — смотрите `reason_code` и
  `warnings` в `km_result`: чаще всего КМ не объявлена в отчёте о валидации
  (`official_baseline_missing`) или объявлена неоднозначно
  (`ambiguous_baseline`). Корзина при этом опубликована.
- **`reconciliation = mismatch`** — построчный пересчёт не воспроизводит число
  из отчёта. Это информация, не дефект ноды: методика отчёта может отличаться
  (например, точность, взвешенная по частотам запросов, против построчной
  невзвешенной). КМ в любом случае заявленная.
- **Нода упала со `spec_error`** — модель не смогла собрать обязательные поля
  формата на этой книге. Первое, что стоит проверить: не многолистовая ли
  книга с разными агентами (задайте `sheet_name`) и корректен ли сам пакет.
- **В книге листы разных агентов** — всегда задавайте `sheet_name`: числовые
  совпадения метрик между листами делают автовыбор ненадёжным.

## Деплой

Нода самодостаточна: никаких импортов из соседних каталогов и из
`monitoring/shared/`. `descriptor.json` перечисляет все исходники в
`script.runConfiguration.sourceFiles` (соответствие диску закреплено тестом);
точка входа — функция `main` в `main.py`. База — `py312-simple`: синтаксис и
stdlib новее Python 3.12 не используются. Зависимости — только
`pandas`, `openpyxl`, `jsonschema`, `requests` (см. `requirements.txt`).

## Глоссарий

- **Корзина** — эталонный набор запросов/ответов агента с оценками, на котором
  проходила первичная валидация.
- **КМ** — ключевая метрика качества агента, объявленная в отчёте о валидации.
- **УМР / формат тестового датасета** — целевой табличный формат контура
  (два листа: «Вариант для отд. запросов» и «Вариант для диалога»).
- **Канон** — внутренний нормализованный фрейм между разметкой и публикацией.
- **Blob-диалог** — весь диалог сессии, упакованный в одну ячейку строки:
  текст с маркерами реплик («КЛИЕНТ: … АГЕНТ: …»), список троек
  `(query_id, вопрос, ответ)`, список пар `(вопрос, ответ)` либо JSON-массив
  сообщений `{"role": …, "content": …}` (роли клиента и агента — по маркерам
  разметки и типовым именам user/assistant, клиент/оператор).
- **Repair** — возврат модели её отклонённого ответа с точной причиной, чтобы
  она исправила JSON сама.
