# laim-baskets-adapter — независимые этапы L / S / K

Нода подключения эталонной корзины GenAI-агента: одна XLSX-книга, отчёт о
валидации, отчёт о разработке и инструкция ассессора. Модель предлагает
разметку, план оценки и упоминания метрик; код проверяет предложения,
строит UMR и выбирает официальную КМ. Модель не переписывает строки корзины
и не выбирает терминальный статус ноды.

Пересборка `fix/stages-rebuild` основана на
`b83bcb4af9446e10059d2de0b59b023fc25acc10`, а не на `research-dev` v3.
Сохраняются четыре входных порта, четыре выходных порта, зависимости и версии
контрактов: `laim-monitoring-metric.v2`, `laim-umr.v2`, `laim-run-report.v1`.
Единственная новая настройка — необязательный `agent_ci`.

## Порты и настройки

Все входы обязательные; платформа передаёт локальный путь к файлу или каталогу
с одним подходящим артефактом. Формат файла проверяется по содержимому OOXML,
а не только по расширению.

| Вход | Содержимое |
|---|---|
| `validation_report` | DOCX-отчёт о валидации; единственный источник официальной КМ для этапа K |
| `test_set` | XLSX/XLSM-корзина |
| `development_report` | DOCX-отчёт о разработке |
| `assessor_instruction` | DOCX либо UTF-8 TXT с инструкцией ассессора |

| Выход | Содержимое |
|---|---|
| `reference_umr` | DataFrame в формате тестового датасета |
| `monitoring_metric` | Контракт `laim-monitoring-metric.v2` с планом и официальным baseline либо причиной `not_computable` |
| `km_result` | Журнал `laim-run-report.v1`, дополненный независимым блоком `baseline` |
| `umr_artifact` | Локальный путь к XLSX с тем же опубликованным листом |

| Настройка | По умолчанию | Поведение |
|---|---|---|
| `model_id` | `glm-5.2` | Модель контурного шлюза; значение и настройка не изменены |
| `sheet_name` | пустая строка | Закрепляет лист; при непустом значении переход на другой лист запрещён |
| `agent_ci` | пустая строка | Переопределяет CI-код из имени пакета; например, `CI09774440` |

`agent_ci` обрезается по краям, проверяется как `CI` + цифры и приводится к
верхнему регистру. Он имеет приоритет даже при другом CI в имени пакета.
Это настройка, а не новый порт `run_context`. Без неё сохраняется прежнее
поведение: CI из имени пакета, а при его отсутствии — имя пакета и предупреждение.
Для временных каталогов платформы следует задавать `agent_ci` явно. Источник
идентичности записывается в `decisions.basket_id_source`. Невалидная настройка
отклоняется до LLM-вызовов.

## Три этапа и независимая деградация

```text
XLSX + три документа
        │
        L: layout → проверка физики → канон → возможность публикации UMR
        │
        ├── S: metric → план оценки → main_metric / информационный пересчёт
        │
        └── K: baseline → цитаты отчёта → официальный baseline / порог
                         │
                  сборка результата
```

S и K выполняются последовательно, но отказ S не отменяет K. Успешный S
передаёт K только имя метрики как подсказку; числовой пересчёт, оценки строк,
инвентарь колонок и остальные документы в запрос K не попадают.

| L | S | K | Результат |
|---|---|---|---|
| Успех | Успех | Одно подтверждённое значение | `computed`, корзина с `main_metric`, официальный baseline |
| Успех | Отказ | Любой результат | `not_computable / score_plan_failed`, корзина без `main_metric`; результат K сохранён отдельно |
| Успех | Успех | Значения нет | `not_computable / official_baseline_missing`, корзина с оценками S |
| Успех | Успех | Неоднозначность | `not_computable / ambiguous_baseline`, корзина с оценками S |
| Отказ после восстановления | Не запускается | Не запускается | `spec_error`: канон для публикации не собран |

При одновременном отказе S и K основной `reason_code` — `score_plan_failed`,
а причина K остаётся в `baseline.reason_code`. Причина каждой деградации
называет этап, ожидание, наблюдение и действие оператора.

### L — структура и канон

Модель получает документы и ограниченный структурный снимок книги: строки
шапки, статистику и примеры колонок, объединения, маркеры диалога. Ответ
`layout` задаёт лист, шапку, роли колонок, группировку, маркеры blob-диалога и
весовую колонку. Детерминированные проверки и правила определения режима
оценки базы v2 сохранены; методология v3 сюда не переносится.

Код проверяет разметку, строит канон и проверяет обязательные поля публикации.
Дефекты возвращаются модели через repair. После исчерпания repair возможны
прежние документированные отбрасывания строк без `input_query`, вне групп или
с неразворачиваемым blob; их номера сохраняются в журнале. Отброс более
половины исходных строк не допускается.

**Запасной лист пробуется только после отказа L**, когда известен неудачный
лист, книга содержит другой лист и оператор не закрепил `sheet_name`.
После получения канона выбор листа окончателен: ни ошибка S, ни ошибка K
не переводит прогон на «Описание», справочник или другого агента.

### S — оценка единиц без baseline

Ответ задачи `metric` имеет ровно поля:

```text
quotes, metric_name, method, sources, reducer,
missing_policy, majority_denominator, scale
```

`reported_value`, `threshold`, `comparator` и терминальный `state` в схеме S
отсутствуют и отклоняются как лишние поля. Методы: `identity`, `accuracy`,
`mean_criteria`, `all_criteria`, `majority`, `all_assessors`. Редьюсеры: `mean`
и `frequency_weighted_mean`. Политики пропусков: `fail`, `exclude_unit`,
`exclude_value`, `zero`. Шкалы: `ratio`, `percent`, `raw`.

Физика источников, нормализация, определение единицы оценки и веса сохранены
из базы. Режимы: `qa` для отдельных ответов, `turn_with_history` для реплик
с историей и `dialogue` для оценки сессии. В `dialogue` одна сессия — одно
наблюдение, независимо от числа её реплик.

**Изменение для формул.** Score-источник может содержать формулы с явно
проверяемыми ссылками только на ячейки своей строки. Например, `=AVERAGE(D2:F2)`
и `=IF(D2=E2,1,0)` в строке 2 допустимы. Межстрочные диапазоны, ссылки на
другие листы/книги, именованные и структурированные ссылки, динамические
`INDIRECT`/`OFFSET` и недетерминированные функции не допускаются. Вертикальные
агрегаты по-прежнему не становятся построчными оценками.

Используются **сохранённые в XLSX значения формул**, а не их выполнение
Python-кодом. В журнал добавляется `formula_score_cached` с колонкой и
номерами строк. Если кеш пуст, действует `missing_policy`; без оцениваемых
единиц S не становится успешным. Перед загрузкой такой книги пересчитайте и
сохраните её в табличном редакторе. Проверка ссылок не доказывает свежесть кеша.

Провал схемы, физики, расчёта либо транспорта после предусмотренных повторов
становится `score_plan_failed`. Публикуется уже собранная корзина без
`main_metric`, затем запускается K.

### K — официальная КМ из отчёта о валидации

Модель получает только отчёт о валидации с нумерацией `p001`, `p002`, …,
имена листов и необязательную подсказку имени метрики из S. Ответ — JSON-массив
всех найденных упоминаний, например:

```json
[
  {
    "metric_name": "Accuracy",
    "raw": "93%",
    "paragraph": "p002",
    "kind": "value",
    "slice_label": null,
    "is_key_metric": true
  },
  {
    "metric_name": "Accuracy",
    "raw": "90%",
    "paragraph": "p003",
    "kind": "threshold",
    "slice_label": null,
    "is_key_metric": false,
    "comparator": ">="
  }
]
```

Виды: `value`, `slice_value`, `threshold`, `ci_bound`, `other`. Модель не
возвращает `declared`, `ambiguous` или `not_declared`: эти состояния выбирает
код. Пустой массив — допустимый ответ, означающий отсутствие упоминаний.

**Проверка свидетельств.** `paragraph` должен существовать в отчёте, `raw`
должен дословно встречаться в нём целым числом, а не частью другого числа.
Нельзя отбросить знак процента или минус. Число разбирается с десятичной
запятой/точкой, пробелами тысяч и необязательным `%`; нечисловые и
непредставимые в JSON значения отклоняются. Непрошедшие проверку цитаты
попадают в `baseline.rejected`; все проверенные упоминания — в `candidates`.

**Выбор.** В первую очередь рассматриваются `slice_value` с меткой,
совпадающей с выбранным листом после нормализации регистра и пробелов либо
по вхождению. Если такого среза нет, рассматриваются общие `value`.
Только чужие срезы без общего значения дают `ambiguous_baseline`, а не
автоматический выбор первого среза. Книга «данные + Описание» сама по себе
не требует, чтобы имя листа было написано в отчёте.

Среди оставшихся кандидатов предпочтительны `is_key_metric`, затем точное
совпадение нормализованного имени с метрикой S. Для одной метрики внутри
одного абзаца используется первое число **по позиции в тексте**, а не
по порядку ответа модели: в строке таблицы значение идёт перед границами ДИ.
`threshold` и `ci_bound` не используются как официальное значение.

Одно значение либо попарно согласованные округлённые значения дают
`declared`; сохраняется наиболее точное представление. Допуск сравнения
кандидатов — половина более грубого опубликованного разряда. Разные
несогласованные значения дают `ambiguous_baseline` с полным списком
кандидатов. Отсутствие итоговых значений — `official_baseline_missing`.

**Шкалы.** `%` в `raw` явно задаёт `percent`; иначе используется домен S.
При отказе S для числа без `%` сохраняется `raw` — неподтверждённая шкала
не угадывается. При сборке K с S выполняется явный перевод процентов в доли
или обратно: `0.9%` — это `0.009` в `ratio`, а не `0.9`. Число без `%` не
переводится в проценты по величине. Нельзя без доказательств смешать `raw`
со шкалой долей/процентов: несогласованность даёт диагностируемую деградацию.

**Порог.** Берётся `threshold` той же метрики, подходящий срезу или общий;
`comparator` по умолчанию `>=`, допустимо также `<=`. При конфликте порогов
публикуется предупреждение `threshold_ambiguous`, порог и вердикт отсутствуют;
само однозначное значение КМ сохраняется. Порог не заменяет baseline.

При транспортной ошибке или исчерпании repair K сохраняются уже рассчитанные
оценки S, а результат становится `official_baseline_missing` с технической
причиной. Отсутствие автоматически извлечённого baseline не доказывает, что
числа действительно нет в исходном документе: оператор проверяет журнал.

## Чтение DOCX

Ридер использует стандартный `xml.etree.ElementTree`, а не регулярные
выражения. Поддерживаются пространства имён WordprocessingML; имена XML-
префиксов и атрибуты `w:tbl`/`w:p` не влияют на чтение. Блоки `body` идут
в исходном порядке; таблицы сериализуются построчно через ` | `; вложенная
таблица остаётся текстом своей ячейки и не дублируется отдельными абзацами.
Заголовки по стилям `HeadingN`/`N` получают `#`-префикс. Инструкции полей,
удалённые фрагменты и рисунки не подмешиваются к основному тексту.

Сохранён существующий лимит текста документа в промпте
`DOCUMENT_CHAR_CAP=120000`; превышение сопровождается предупреждением.
Это не гарантия извлечения из не переданной модели части длинного отчёта.
Проверка `raw` проводится по тому же структурному тексту, которому присвоены
номера абзацев.

## Публикация и контракты

`reference_umr` остаётся одним из двух листов спецификации:
«Вариант для отд. запросов» либо «Вариант для диалога». Сырые колонки книги
не подменяют канонические поля. В диалоговом формате `dialogue` содержит
тройки `(query_id, input_query, output_answer)`; при взвешенном редьюсере
сохраняется `input_query_count`. `main_metric` присутствует при успешном S,
даже если K не дал baseline. При провале S колонка не фабрикуется.

В успешной сборке официальное значение берётся из отчёта. Пересчёт корзины
публикуется рядом как `recomputed_value`; `reconciliation: mismatch`
остаётся информационным результатом v2, а не попыткой подогнать официальный
baseline. Допуск сверки — один последний опубликованный разряд, сохранённый
при явном переводе шкалы. Само расхождение не вызывает смену листа или плана.

`km_result` сохраняет контракт `laim-run-report.v1` и прежние блоки `km`,
`stages`, `decisions`, `warnings`, `llm`, `dropped_rows`, `input_sha256`.
Добавляется `baseline`:

```text
state: declared | not_declared | ambiguous
value, raw, paragraph, metric_name, scale
candidates: все проверенные упоминания с parsed_value, position, selected
rejected: исходный кандидат и причина отклонения
threshold: значение, шкала, цитата, абзац, comparator либо null
reason_code, reason, warnings
```

При деградации основной `reason_code` и `reason` записываются также в корень
журнала. Успешный прогон без repair содержит три LLM-задачи: `layout`,
`metric`, `baseline`. В `stages` они записаны как `layout`, `metric`, `baseline`
после `read`. Детали доступны в порту `km_result`, а не только в stdout.

## Границы восстановления

После сборки канона ошибки S/K не отменяют публикацию. Это правило для
прикладных этапов, а не обещание пережить отказ файловой системы или процесса.
Битый пакет, нечитаемый обязательный файл и невалидная настройка отклоняются
до L; невозможность собрать канон — `spec_error`; ошибки записи артефактов
по-прежнему требуют исправления инфраструктуры.

LLM сохраняет транспортные повторы, пробу `response_format: json_schema`
с откатом при HTTP 400 и до трёх попыток structured-output/repair на задачу.
Для K поддерживается корневой JSON-массив, для L/S — объект. Валидация схемы
выполняется локально независимо от поддержки structured output шлюзом.

## Проверка и деплой

Нода самодостаточна: точка входа `main.py:main`, база `py312-simple`, Python
3.12. Runtime-зависимости неизменны: `pandas`, `openpyxl`, `jsonschema`,
`requests`; диапазоны версий заданы в `requirements.txt`. Новых зависимостей
для XML, формул или baseline нет.

```bash
python -m pip install -r requirements.txt pytest 'ruff==0.15.5'
ruff check .
python -m pytest -q
```

Тесты проверяют отдельные этапы, их независимые отказы, сохранение листа,
цитаты/срезы/пороги/ДИ, округление, реальные XML-структуры DOCX, формулы с
кешем и без него, настройку CI и неизменность descriptor относительно базы.
`tests/base_descriptor.json` фиксирует исходный контракт; допускаются только
новая настройка `agent_ci` и новый runtime-файл в `sourceFiles`.

ZIP ноды содержит `descriptor.json` в корне, все `sourceFiles`, README и
`requirements.txt`. Исходники с тестами и протокол проверки поставляются
отдельно. После упаковки проверяются комплектность, SHA-256 и запуск тестов
непосредственно против распакованного ZIP.

**Приёмка:** unit/FakeClient-тесты не заменяют прогон исходных 19 пакетов
Sonnet и Haiku тем же `claude -p` runner. Такой прогон и его результаты должны
быть приложены отдельно, без вывода «19/19» из синтетических тестов.
Платформенная приёмка с `gigachat-3-ultra` по `CI09774440` и паре 438/554
выполняется владельцем. До неё сборка не считается принятым production-релизом.

## Карта кода

```text
main.py                       четыре входа/выхода, настройки, контракт v2
laim_basket/pipeline.py        L → S → K, независимая деградация, публикация
laim_basket/llm/tasks.py        контексты и вызовы трёх LLM-задач
laim_basket/llm/prompts.py      раздельные инструкции и входы L/S/K
laim_basket/llm/schemas.py      схемы layout, score plan, baseline candidates
laim_basket/llm/client.py       JSON-объект/массив, transport, repair
laim_basket/resolve.py         прежняя физика разметки и режимов v2
laim_basket/metric/resolve.py  только физика плана S
laim_basket/metric/baseline.py цитаты, выбор K, сборка с S
laim_basket/metric/engine.py   детерминированный расчёт единиц и пересчёт КМ
laim_basket/reading/           OOXML-пакет, гриды XLSX, XML DOCX, формулы
laim_basket/transform/         группировка, канон, идентичность и значения
laim_basket/publish.py         проекция в формат тестового датасета
laim_basket/export/umr.py       XLSX
laim_basket/journal.py         журнал laim-run-report.v1
```
