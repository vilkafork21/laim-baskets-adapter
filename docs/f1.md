# Неаддитивные КМ: F1

Два разных определения поддерживаются явно. Название «F1» не выбирает
формулу автоматически. Порядок операций берётся из методики; baseline
по-прежнему только из отчёта валидации и не подгоняет расчёт.

## Гармоническое среднее средних

`method=harmonic_mean_of_means` требует ровно по одному источнику с ролью
`precision_component` и `recall_component`. Это могут быть экспертные оценки,
а не TP/FP/FN. После нормализации: P = sum(w*p)/sum(w), R = sum(w*r)/sum(w),
F1 = 2PR/(P+R). Среднее построчных F1 — другая метрика, здесь не вычисляется.

Пример фрагмента плана S (остальные обязательные поля как у прежних методов):

```json
{
  "metric_name": "F1-мера",
  "method": "harmonic_mean_of_means",
  "sources": [
    {"column_id": "C", "role": "precision_component", "normalization": {"0": 0, "1": 0.5, "2": 1}, "polarity": "direct"},
    {"column_id": "D", "role": "recall_component", "normalization": {"0": 0, "1": 0.5, "2": 1}, "polarity": "direct"}
  ],
  "assessment_mode": "qa",
  "reducer": "mean",
  "missing_policy": "exclude_unit",
  "majority_denominator": null,
  "scale": "ratio",
  "metric_options": {"zero_division": 0},
  "quotes": {"method": ["Дословное основание формулы из документа"]}
}
```

`exclude_unit` исключает всю неполную пару; `exclude_value` использует отдельные
знаменатели компонентов; `zero` явно заменяет пропуски нулём; `fail` отклоняет
план при пропуске. Совсем отсутствующий компонент при исключении не превращается
в ноль. При `zero_division=fail` нулевой знаменатель приводит к отказу S;
0 или 1 публикуются только если соответствующая политика явно задана.

`scale=ratio` или `percent`; raw для F1 не допускается. Для исходной шкалы
0/1/2 нужен value_map. Нормализованные компоненты в UMR сохраняются как
`*_metric`; исходные 0/1/2 не выдаются за доли. В `quotes.naming` можно сохранить
дословные конфликтующие подписи отчёта: они попадут в `metric_naming_review`.
Это диагностическое предупреждение, не автоматическое разрешение конфликта.

## Классификационный F1

`method=classification_f1`, источники: один `prediction` и один `target`,
оба `normalization=label`, `polarity=direct`. Поддерживаются скалярные классы
single-label binary/multiclass, не multilabel-массивы и не token-F1.

```json
{
  "metric_options": {
    "average": "macro",
    "labels": null,
    "positive_label": null,
    "zero_division": 0
  }
}
```

Все четыре параметра обязательны. Для `binary` нужен строковый `positive_label`
и `labels=null`. `micro` суммирует TP/FP/FN, `macro` усредняет F1 классов,
`weighted` взвешивает F1 классов по поддержке target. Формула класса:
2TP/(2TP+FP+FN). Нулевой знаменатель — только случай TP=FP=FN=0; отсутствие
верных предсказаний при наличии ошибок НЕ даёт единицу при zero_division=1.

`labels=null` означает объединение классов target и prediction после исключения
неполных пар; явный список задаёт включаемые классы, включая отсутствующие.
Ошибки между выбранным и внешним классом учитываются. Для устойчивого мониторинга
фиксируйте список классов по методике: изменение домена при labels=null меняет
состав macro/weighted. При нулевой сумме поддержек weighted использует среднее
определённых политикой F1 выбранных классов, как sklearn. `zero_division=fail`
не препятствует micro, когда общий знаменатель ненулевой, хотя отдельный класс
может отсутствовать; в диагностике его F1 равен null.

Пропуски классов: только `fail` или `exclude_unit`. `zero` не означает автоматически
класс 0, а `exclude_value` не определяет матрицу ошибок, поэтому они отклоняются.
Ключи классов нормализуются по существующим правилам ноды (регистр/пробелы/ё).

Для ОБОИХ методов reducer означает вес единицы: `mean` — равный вес;
`frequency_weighted_mean` — целые положительные частоты из физической колонки.
Это не финальное усреднение F1. В режиме dialogue одна группа учитывается один
раз, а не по числу реплик. Взвешивание строк и average=weighted — разные операции.

## Публикация и совместимость

Порты, настройки, runtime-зависимости и идентификаторы v2/v1 не изменены.
Для прежних методов структура контракта не меняется. Для новых методов
семантика расширена и требует обновлённого потребителя:

- `score_column=null`, `score_scope=dataset`: построчного `main_metric` НЕТ.
- `required_capabilities=["laim.nonadditive-metrics.v1"]`.
- `aggregation.method` — `harmonic_mean_of_means` или `classification_f1`,
  НИКОГДА не `mean`; `sample_weighting` — `uniform`/`frequency`.
- `scoring.sources` ссылается на опубликованные нормализованные компоненты или
  метки классов; `scoring.metric_options` сохраняет полное определение.
- `km_result.km.aggregation_statistics` сохраняет точные суммы и знаменатели
  компонентов либо TP/FP/FN/support по классам. Числа хранятся Decimal-строками.
  Статистики относятся к reference, их нельзя подставлять вместо новых данных.

Старый агрегатор, умеющий лишь усреднять `main_metric`, НЕ подходит. Потребитель
должен проверить required_capabilities и method и отказать при неизвестном
значении. Это требование контракта; данный репозиторий не может обеспечить его
исполнение в старых внешних нодах. Не усредняйте F1 батчей: суммируйте компоненты
и знаменатели/счётчики и вычисляйте F1 в конце. Корреляция построчного main_metric
для такой метрики не определена: сравниваются компоненты/классы и итог выборки.

Несовпадающие F1 macro/micro в baseline остаются неоднозначностью. Равенство
чисел не доказывает равенство методик. Явная привязка проверенного плана к одной
подписи отчёта не превращает прикладную формулу в классификационную.

## Проверка

`pytest` покрывает метод, шкалы, пропуски, классы, веса, dialogue, публикацию и
независимость K. `python tools/check_f1_oracle.py --out /tmp/f1-oracle.json`
проверяет 1600 синтетических задач через scikit-learn (QA-зависимость, не runtime).
`tools/verify_arithmetic.py` независимо пересчитывает reviewed-корпус с Fraction.

Ни один из этих запусков не заменяет живой LLM-прогон и приёмку внешних нод.
